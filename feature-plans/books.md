# Books

Tracks rough edges and follow-up work for the Books domain (Book / Version / ReadInstance). Descriptive content lives in `/documentation/books.md`.

## Known limitations

### Authorization

- **Books have no policy.** `BookListPolicy` is still the only one in the app; `BookController` never calls `authorize()`. Note the catalog being shared between accounts is deliberate — see `/documentation/books.md` — so what's missing here is not ownership but a guard on the *destructive* operations.
- **Discarding a copy is not audited.** `PATCH /versions/{id}/discard` records no actor and no system timestamp for the flip. `discarded_at` is the user-supplied real-world date, not a system one; `updated_at` gets clobbered by unrelated edits. With a second account this becomes "who got rid of this and when".

### Data integrity

- **`DELETE /books/{id}` is still open, just uncalled.** The SPA's Delete button is gone and discarding is the soft delete (see `/documentation/books.md`), but the route is registered for any authenticated user. It hard-deletes the book's versions and read instances and prunes authors left with zero books — no undo, no audit trail. Nothing in the app reaches it; a hand-written request still can. Closing it is "Unlock book delete as an admin-only action" below.
- **`rating` still lives doubled in the column.** The mutator/accessor pair means nothing going through Eloquent has to know that, but query-builder writes still store the un-doubled value (displaying at half the intended rating) and query-builder reads still return double. Storing ratings in their natural units would remove the trap entirely — see Future improvements.
- **`read_instances` still carries `book_id` alongside `version_id`.** The invariant is enforced model-side, but the dual-attach is a holdover — see Future improvements.
- **Discarded copies still count toward statistics and lists.** Aggregating reads over discarded copies is intentional — you read the book, discarding it later doesn't undo that. But `ListItem` references `version_id` with no discard awareness, so a list can point at a copy you no longer own and nothing surfaces that. `ListItemsTable` doesn't render the state either.
- **Deleting a book deletes every account's reads of it, by design.** `BookController::destroy` lifts `BelongsToCurrentUser` deliberately (`withoutGlobalScope`) so no rows are orphaned against a deleted `book_id`. Correct, and it is the reason delete has to be admin-only before the SPA can offer it again.

### Performance & query shape

- **`getCompletedItemsForYear` fetches every book for the year and sorts in PHP.** No pagination, no DB-side ordering on the outer query. Will degrade as read history grows — and it is now the only book listing whose ordering isn't a query parameter.

### API surface

- **`BookController::update` silently drops new read instances.** Rows with no `read_instance_id` are filtered out before the update runs. The UI has no affordance for adding one from the edit view, so this is invisible today — but if the form is ever wired to send new entries, they vanish.
- **`BookController::getBooksByFormat` is dead code.** Not in `routes/api.php`, and uses `$format->id` instead of `$format->format_id`, so it would 500 if called.

### Frontend

- **Three date formatters, no shared home.** `BookServices.formatDateRead` renders `MM/DD/YY` (only `EditBookView` uses it), `libraryList.monthYear` renders `Mar 2022`, and `bookDetail.fullDate` renders `12 Mar 2022`. The month table is shared — `bookDetail` imports `MONTHS` from `libraryList` — but the functions are spread across a service and two utils. A `utils/dates.js` holding all three is the tidy version; it was left alone here because moving `formatDateRead` means touching `EditBookView` and its spec for no behavior change.
- **`BookServices.calculateRuntime` and `bookDetail.runtimeLabel` format the same column differently.** `0h 45m` for a fixed-width table cell (`EditBookView`), `45m` for inline prose (the book page). Both renderings are right for where they are, but the pair should converge on one function with a padding option when `EditBookView` is next touched.
- **The book page's copy list has no ordering control and no pagination.** `orderedCopies` puts owned copies ahead of discarded ones and stops there. Fine at one to three copies; a book with a dozen would want the discarded ones collapsed behind a toggle.
- **`readsByCopy` silently drops a read with a null `version_id`.** The column is nullable in the schema even though every write path sets it, so such a row would appear in the reading history with no copy named (correctly) but would not be counted against any copy. Dropping `read_instances.book_id` (Future improvements, "Drop `book_id` from `read_instances`") is the moment to decide whether `version_id` should be `NOT NULL`.
- **`capitalize` on genre runs is applied to the container, not the links.** Both `LibraryBookRow` and `BookView` put `capitalize` on the wrapping element with `, ` separators in sibling spans. It renders correctly today, but the CSS rule keys on whitespace boundaries, so it is one markup change away from capitalising a separator instead of a genre. Putting the class on each link would make it deterministic.
- **`BookServices.js` is the only file in `resources/js/services/`.** The "service orchestrates stores" pattern that CLAUDE.md describes exists for books and nothing else; the convention isn't really established yet, just claimed.
- **No optimistic updates on read-instance creation.** UI waits for the round trip; on slow connections the rating widget feels laggy.
- **Discarding is only reachable from the book detail page.** `BookCopyRow` owns the affordance, so there is no way to discard from the library listing, from a list, or in bulk — awkward for the exact case that motivated the feature (a backlog of copies got rid of years ago). A bulk "mark these as discarded" surface, and a `discarded` column in the bulk-upload CSV contract, are the obvious follow-ups.
- **The discarded shelf reuses `LibraryView` wholesale.** A row shows one `Discarded <month year>` — the latest `discarded_at` across the book's discarded copies — so a book with two discarded copies shows one date, and there is no restore affordance from the shelf.
- **Sorting stops at the library.** `AuthorView`, `GenreView`, `FormatView`, `CompletedView` and `ListStatisticsView` all render `BookshelfTable` without the `sortable` prop, so their headers are inert. They don't fetch through `GET /books`, and each backing endpoint would need its own `?sort=` before the prop could be turned on. `CompletedView` is the one users will ask for first. Note the library itself no longer renders `BookshelfTable` (2026-09-15, see `/documentation/books.md` → The library page); the sortable table is now used by nobody, so when the remaining listings gain `?sort=` the choice is between switching on `sortable` there or moving them onto the library's row + section components, which take a `sortKey` rather than sortable headers.
- **The library's section headings are only right when the server's order agrees with them.** `groupBooks` folds *adjacent* equal headings, so it depends on `BookListing::sort()` keeping equal group values contiguous — true today for every key, but a future sort key needs a matching `group` in `SORT_OPTIONS` (or a pass-through one) or the page renders a heading per row. The registry is the seam; the coupling is undocumented anywhere the backend would see it.
- **No letter / year jump on the library.** Sections give the page structure but there is no way to jump to "M" or "2021" the way `GenresView`'s letter strip does — that needs a server-side `?letter=` (a `HAVING` on the `sort_author` alias) or a facet-count endpoint, both deliberately left out of the first pass.
- **No genre or location filter on the library.** Status, shelf and format are filters; genre and shelf location are still separate pages (`/genres/:id`, `/locations/:slug`), so "unread science fiction" is not expressible. `?genre=` on `GET /books` is the obvious next parameter; facet counts would be the moment to add a `meta` block to the response.
- **`sortablejs` and `sortablejs-vue3` are still in `package.json` with no importer.** They backed a drag-to-reorder block in `BookshelfTable` that no view ever enabled; removing it left the dependencies orphaned. List reordering persists through `PATCH /lists/{id}/reorder` and doesn't use them.
- **`BookTableRow`'s `"Unknown"` fallbacks can never render.** `authorInfo()` and `bookFormat()` each return either an object (`{ name, slug }`) or the bare string `"Unknown"`, and the template only ever reaches for `.name` and `.slug` — which a string doesn't have. So a book with no authors renders a `router-link` to `params: { slug: undefined }` with an empty label: a broken link where the author's name belongs, and the word "Unknown" the fallback exists to show never appears. Same for a book with no versions on the desktop row's format link. The fix is to make the fallbacks return the right *shape* (`{ name: "Unknown", slug: null }`) so the existing `v-if="bookFormat.name"` guard starts doing its job, rather than to add string checks at each of the five call sites. (The library row, `LibraryBookRow`, does this right via `utils/libraryList.js` — shaped fallbacks, guarded version access, three genres plus `+N` — but the other listings still render `BookTableRow`.)
- **`BookTableRow::pageCount` is unguarded, directly below a guarded sibling.** It reads `this.book.versions[0].page_count`; `bookFormat()` five lines up checks `versions.length > 0` first. A book with zero versions throws `Cannot read properties of undefined` and takes the whole row's render with it — and "books with zero versions" is a state `/feature-plans/admin.md` ("Catalog integrity dashboard") already expects to find in the catalog. (The library row, `LibraryBookRow`, does this right via `utils/libraryList.js` — shaped fallbacks, guarded version access, three genres plus `+N` — but the other listings still render `BookTableRow`.)
- **`BookTableRow::primaryGenres` disagrees with itself three ways.** It's named "primary", its comment says "first 3 genres", and it slices `(0, 2)`. Decide which is intended; two of the three are wrong either way. See `/feature-plans/genres.md` for the UX side of how many genres a row should show. (The library row, `LibraryBookRow`, does this right via `utils/libraryList.js` — shaped fallbacks, guarded version access, three genres plus `+N` — but the other listings still render `BookTableRow`.)
- **`BookTableRow::primaryGenres` re-maps a custom PK onto a generic `id`.** It projects `genre_id` → `id`. The projection is internally correct and the pattern is defensible in isolation, but it leaves a place in the SPA where `:key="x.id"` is *right*, in a codebase whose one hard rule about primary keys is "never `id`" — visually identical to the real `:key` bug `FormatsList` carried for months, so a reader auditing for that bug class has to open the script block to clear a false positive. Either keep the custom key name in the projection, or leave a comment at the binding. (`BookView::readHistory` was the other one; `utils/bookDetail.js` keeps `read_instance_id` as-is.)

## Future improvements

In rough priority order — earlier items unblock later ones.

1. **Unlock book delete as an admin-only action.** Discard covers "I don't have this any more", so what's left for delete is removing rows that shouldn't exist — junk entries, and the loser of "Merge a duplicate book into another". It needs, in order: the admin gate from `/feature-plans/admin.md` ("Foundations"), applied to `BookController::destroy` so the route stops being open to every account; a `ConfirmAction` whose impact names the copies, the reads per account, the lists holding a copy, and the authors that would be pruned (a dry-run response from the endpoint, same unforced-first shape as genre delete); and an entry in the admin audit log. The surface is `/admin/books` or a gated button on the edit page, whichever the admin shell makes natural. Soft deletes are not a prerequisite: with discard as the everyday path, an admin-only delete behind an impact confirm is acceptable as a hard delete.
2. **Store ratings in their natural units and migrate existing data.** The halving accessor shipped (2026-08-09), so the mutator-without-accessor asymmetry that kept producing display bugs is gone — but the column is still doubled, so `DB::table()` on `read_instances` remains a trap and `avg()` still has to divide. A `decimal(2,1)` column would close it.
3. **Drop `book_id` from `read_instances`** and derive it through the version relation. The model-level cross-table validator is in place, but the dual-attach itself has no clear benefit.
4. **Sort the other book listings.** `GET /books` grew `?sort=` / `?direction=` (see `/documentation/books.md`), and `BookshelfTable` takes a `sortable` prop, but only the library passes it. Each remaining consumer needs its endpoint to accept the same two parameters before its headers can come alive — `CompletedView` first, which pairs with "Paginate `getCompletedItemsForYear`". Reuse `BookListing::SORTABLE`'s key names so one set of column keys means the same thing everywhere. `GenreView` is the cheapest of the remaining ones: its endpoint already builds on `BookListing`, so the backend half is passing `?sort=` / `?direction=` through to `BookListing::sort()` and the rest is the URL handling `LibraryView` already models.
5. **Paginate `getCompletedItemsForYear`** and move sorting to the DB. Now the odd one out: it's the only book listing that orders in PHP over an unbounded fetch.
6. **Delete `BookController::getBooksByFormat`** (dead and broken). Coordinate with `/feature-plans/formats.md` item 1, which decides whether the `?format=` filter moves to it or absorbs it.
7. **Optimistic UI for read-instance create** in `BooksStore` — push the row into local state immediately, reconcile on response.
8. **Add a policy guarding destructive book operations.** Not ownership — the catalog is shared on purpose — but discard (and, once unlocked, `destroy`) are the operations where a second account can undo the other's work. Cheapest useful version is an audit trail plus a confirm-with-impact-summary; the confirm component now exists (`components/globals/ConfirmAction.vue`, see `/documentation/admin.md`), the audit trail is `/feature-plans/admin.md` item 3.
9. **Decide whether `is_discarded` / `is_on_loan` collapse into an `ownership_state` enum before "wishlist" lands.** On loan shipped as a parallel `is_on_loan` column (plus `loaned_to` / `loaned_at`) rather than an enum. Two reasons: the lent state carries its own detail (`loaned_to`) that an enum's single `state_changed_at` couldn't hold, and the loan deliberately overlays the shelf rather than being a place of its own. The cost is that "discarded and lent" is representable and is kept out only by code, at three doors: `VersionController::discard` ends a loan, `lend` refuses a discarded copy, and the importer fails `loan_on_discarded_copy`. A wishlist state (not owned, never shelved) would be the third flag, and that is where an enum (`owned` / `on_loan` / `discarded` / `wishlist`) starts paying for itself. If it happens, the CSV keeps `is_discarded` / `is_on_loan` as its vocabulary so old exports still import.
10. **Make the remaining book-row computeds return one type each.** `BookTableRow::authorInfo` / `::bookFormat` (object-or-`"Unknown"`), plus a guard on `BookTableRow::pageCount`. (`BookView::readHistory`, the array-or-`""` one, is gone — `utils/bookDetail.js` replaced it.) All three are logged under Known limitations above and in `/feature-plans/read-history.md`; they're one small separable commit, and fixing the shapes is what makes the `v-if` guards already sitting in those templates start working. Worth pairing with a component-testing setup (`/feature-plans/frontend-tests.md`) — every one of these is invisible to the current suite, which is why they survived this long. Sorting raises the stakes on `pageCount`: a versionless book can now be pulled onto page 1 by `?sort=pages`, where before it sat wherever author order put it.
11. **Merge a duplicate book into another.** Renaming a mis-entered duplicate onto an existing title leaves two books under one title (the second gets a `-<author>` slug) with no SPA path to combine them — the 2026-09-29 "Fellowship of the Ring(s)" duplicate was fixed by hand in SQL. The operation: re-point the loser's `versions` (and `read_instances.book_id`, until item 3 drops it) at the kept book, then delete the loser's `book_author` / `book_genre` rows and the book itself, in one transaction. Authors and genres stay the kept book's; the confirm should show both sets so a difference isn't silently lost. Same N→1 shape as the genre and author merges (`GenreService::merge`, `AuthorService::merge`), and a destructive operation for item 8's guard to cover.
